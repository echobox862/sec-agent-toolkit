# 靶场笔记写作

## When to Use

三种情况：

- 刚做完一个靶场实验，记录散在 Burp 截图、终端输出和脑子里，要整理成一篇能给别人看的笔记。
- 已有笔记只有步骤没有原理，面试官追问"为什么能成"时答不上来。
- 笔记写完了，不确定能不能公开，需要过一遍红线。

不适用：漏洞扫描、批量验证、生成可直接使用的载荷。这个技能只处理文档。

## Prerequisites

- 一份授权环境下的实验记录。没有授权前提的实验不写，也不发布。
- 记录里至少有：请求长什么样、改了哪个参数、响应有什么变化。
- 目标信息（域名、账号、flag、IP）在动笔前就该替换成代号。

## Workflow

1. **定题。** 一篇只讲一个点。标题就是索引，写「文件上传——黑名单双写绕过」，不写「文件上传综合笔记」。一个点讲透，比五个点各讲一半有用。

2. **先归因，再写。** 用 `references/frameworks.md` 里的两条框架判断：
   - getshell 三元组：能写进去、能访问到、能被解析。三条同时成立才算打通。
   - 绕过统一原理：过滤在字符串层，解析在语义层，缝隙在两者不一致的地方。
   
   归不出结论，说明还没想明白，先回去补实验，不要动笔。

3. **按六段填。** 现象、原理、复现、危害、修复、延伸。原理和修复两段最值钱：
   - 只写「改了个包就绕过了」，读的人会认为在跟教程。
   - 写「这个字段由客户端声明、可伪造，服务端拿它做判断就等于信任了不可信输入」，才说明理解了机制。

4. **框架不适用就明说。** 越权类漏洞输入合法、解析正确，坏在业务规则，两条框架都不适用。写清楚为什么不适用，比硬套框架更能说明理解到位。

5. **脱敏。** 按 `references/redlines.md` 的规则替换：域名、账号、flag、凭据、内网 IP、绝对路径。只保留理解原理必需的技术内容。

6. **跑检查。** `python scripts/check_redlines.py 笔记.md`。high 项必须清零才能发布，medium 项逐条确认。

7. **更新索引。** 在仓库的 writeups/README.md 里加一行，标注漏洞类型和归属框架。

## Verification

发布前逐条确认：

- 六段齐全，没有用「略」跳过原理或修复。
- 原理段能回答「为什么成立」，而不只是「怎么操作」。
- 框架归因有明确结论，包括「不适用」的情况和理由。
- `check_redlines.py` 输出 high 为 0。
- 文中出现「授权测试环境」的说明。
- 没有可直接使用的完整攻击载荷，验证只用到 `echo`、`whoami` 这类最小命令。

## 这个技能不做的事

- 不生成 payload、不写利用脚本。
- 不判断漏洞真伪，那要靠复现和证据。
- 不替实验下结论。没做过的步骤不要写进去，面试一定会追问细节。
