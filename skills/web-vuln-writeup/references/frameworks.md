# 两条判断框架

写每一篇笔记之前先过这两条。它们管的不是同一件事：

- 框架一回答「这条链能不能打通」，是能力边界问题，结论是通或不通。
- 框架二回答「过滤器为什么没拦住」，是实现缺陷问题，结论是缝隙在哪、怎么补。

---

## 框架一：getshell 三元组

**能写进去 + 能访问到 + 能被解析。**

三条同时成立，利用才成立；缺任意一条，链条就断在那里。

| 路径 | 能写进去 | 能访问到 | 能被解析 |
| --- | --- | --- | --- |
| 文件上传 | 上传接口接受了内容未被清洗的文件 | 落盘路径可从 Web 访问，或能通过路径穿越放进站点根 | 后缀在服务端脚本解析范围内，且目录允许执行 |
| WAR 部署 | 管理后台的部署功能本身就是为写文件设计的 | 包名成为上下文路径，包内文件名成为访问名 | 包内放脚本文件，由中间件自身解析 |
| 数据库写文件 | 数据库账号有文件写权限，且写入目录未被限制 | 写入路径落在 Web 根目录内 | 写入内容是服务端脚本，目录允许执行 |

### 为什么是三个条件，不是一个漏洞

三条分属三个组件：写入能力来自业务功能，访问能力来自 Web 服务器与目录配置，解析能力来自语言与解析器配置。任何一条都由不同的人在不同时间配置，所以它们经常不同时成立，加固时也经常只补上其中一条。

两个直接结论：

- **测试时当检查表用。** 写不进去就找别的写入通道；写进去了访问不到就找路径泄露或穿越；能访问但被当静态文件下载，就去试后缀和解析配置。
- **防御时打断任意一条即可，打断「能被解析」最省事。** 把上传目录、数据目录设成禁止脚本执行，写入类漏洞的收益就归零，比逐个过滤上传内容可靠。

### 容易记错的一点

「能写进去」不等于「上传成功」。上传返回 200 只说明第 1 条满足。真正要验证的是第 3 条：访问一次，看返回的是文件内容还是被执行的输出。

## 框架二：绕过的统一原理

**过滤发生在字符串层，解析发生在语义层；两者不一致的地方，就是缝隙。**

各种听起来不同的绕过手法，本质是同一件事：过滤器检查的字符串形态，和程序最终解析出的语义，不是同一个东西。

| 形态 | 过滤器看到的是 | 程序最终执行或落点 |
| --- | --- | --- |
| 关键词双写 | 中间夹了一层多余字符，看起来不含敏感词 | 过滤只做一次替换且替换为空，反而把多余层消掉、还原出关键词 |
| 变量拼接、参数交叉引用 | 每个参数单独看都是无害碎片 | 程序把碎片拼回完整表达式后再解析 |
| 路径穿越 | 路径字符串以允许目录开头，前缀检查通过 | 文件系统把 `..` 消解掉，落点在允许目录之外 |
| 编码、大小写、空白变体 | 命中不了关键词正则 | 解析阶段等价于原关键词 |
| 空字节截断 | 字符串被截断，被检查的后半段不存在 | 底层按 C 字符串规则在空字节处终止 |

### 顺着它把「试 payload」变成「先猜实现」

1. 先判断这个位置的过滤是字符串操作还是语义操作：是一次 `replace`、黑名单正则，还是前缀判断。
2. 再判断下一层会怎么解析这串字符：会不会二次替换、会不会消解路径、会不会按字节长度判断。
3. 两者的差异点就是可构造的位置。构造完要验证解析结果，而不是只看有没有弹窗或报错。

顺序也会影响结果。有的过滤器按顺序依次删除多个关键词，构造时必须考虑删除的先后，顺序错了就拼不出目标，靠穷举是碰不出来的。

### 它同时解释了为什么黑名单不行

黑名单只能列举已知危险项，而达到同一效果的手段枚举不完。任何只做字符串层过滤的方案，都会在这条原理下被反复绕过。

修复的重心不是把过滤写得更全，而是让字符串层与语义层合一：

| 漏洞类型 | 消解差异的做法 |
| --- | --- |
| SQL 注入 | 参数化查询或预编译，让数据永远不进字符串拼接 |
| XSS | 按输出上下文编码，让数据在语义上永远是数据 |
| 路径穿越 | 路径规范化后再做前缀判断，而不是先判断再交给文件系统 |
| 命令执行 | 不经 shell、参数数组传递、白名单枚举 |

## 两条框架怎么配合

一篇笔记的「原理」一节把这两条走完，「修复」一节自然有了层次：先用框架二定位补齐方式，让过滤与解析一致；再用框架一决定打断哪一环，改配置最彻底。

归因结论只有三种：成立、不成立、不适用。不适用也要写理由，这是判断，不是省事。
